How OpenTTD Works

A plain-language tour of a 410,000-line simulation game — written for programmers who have never touched C++ or this codebase.

OpenTTD master · 1,383 files · C++20 · compiled from the source tree

OpenTTD is an open-source reimplementation of Transport Tycoon Deluxe: you build railways, roads, airports and shipping lanes, and haul cargo between towns and industries for money. This page is about the program, not the game — how 410,000 lines of C++ are organised, and why they are organised that way.

You do not need to know C++. Where a C++ idiom matters, it is explained in passing. What you do need is the willingness to accept one strange idea early, because almost every design decision in this codebase follows from it.

1What kind of program this is

Most applications you have worked on are reactive: something happens (a click, a request), code runs, state changes, the screen updates. Idle programs do nothing.

OpenTTD is not like that. It is a simulation that advances whether or not you touch it. Trains keep moving, towns keep growing, industries keep producing, competitors keep building. The program's job is to advance one enormous shared world — millions of map tiles, thousands of vehicles, hundreds of stations — in small fixed steps, forever.

Now add the requirement that makes it genuinely hard:

In a multiplayer game, every player's computer runs its own complete copy of the simulation. Nobody sends world state over the network. Each machine must independently compute bit-for-bit identical results, forever, or the game falls apart.

That is the constraint. It is why the map is a packed byte array rather than a tree of objects; why nothing changes the world except through a formal "command"; why the random number generator is deliberately predictable; why saved games from 2004 still load. Nearly every "why is it done like that?" in this codebase traces back to determinism.

C++ in sixty seconds, if you need it

C++ splits code into two kinds of file. A header (.h or .hpp) declares what exists — the names, types and shapes of things — and other files "include" it to learn about them. A source file (.cpp) contains the actual implementation. When one file uses another's function, it includes that file's header.

Two consequences show up constantly here. Including a header is a literal textual paste, so a widely-included header like stdafx.h makes 556 files recompile when it changes. And unlike Python or JavaScript, nothing is discovered automatically: every source file must be listed by hand in the build configuration, or it is simply never compiled — with no error at all.

3The heartbeat

At the centre of the program is a loop that runs roughly 30 times per second. Each pass is called a tick, and a tick advances the entire world by one step. The function is StateGameLoop(), and reading it is the fastest way to understand what the game actually does:

AnimateAnimatedTiles();       // level crossings, windmills, animated industry
TimerManager<TimerGameCalendar>::Elapsed({});
TimerManager<TimerGameEconomy>::Elapsed({});
TimerManager<TimerGameTick>::Elapsed(1);
RunTileLoop();                // trees grow, towns spread, fields appear
CallVehicleTicks();           // every train, lorry, ship and plane moves
CallLandscapeTick();          // industries produce cargo
AI::GameLoop();               // give the AI opponents a slice of time
Game::GameLoop();             // and the scenario script, if any

That is the whole simulation, in order, every tick. Everything else in the codebase is either called from one of those lines, or exists to draw the result on screen.

Note what is not there: no rendering. Drawing happens on a separate schedule, reading the world state without changing it. If the display cannot keep up, the simulation is unaffected — which matters, because all machines in a multiplayer game must tick in lockstep regardless of their frame rate.

Four different clocks

Confusingly but usefully, the game tracks time four separate ways, and picking the wrong one is a common bug.

ClockMeasuresUsed for
TickSimulation stepsVehicle movement, anything needing fine granularity
CalendarIn-game dates, with leap yearsVehicle introduction dates, the displayed date
EconomyFixed 30-day months, 360-day yearsFinances, cargo payments, company accounts
RealtimeActual wall-clock secondsInterface only — tooltips, animations, autosave

Calendar and economy time used to be the same thing and can now diverge, which is why they are separate. Realtime is the dangerous one: it must never influence the simulation, because two players' clocks are never identical.

4The world is one big array

The map is not a grid of objects. It is a flat array of small fixed-size records, and a tile reference (TileIndex) is just an index into it.

Each tile occupies 12 bytes, split across two arrays:

struct TileBase {          // 8 bytes, every tile
    uint8_t  type;         // what this tile IS (rail, road, water, house...)
    uint8_t  height;       // height of the northern corner
    uint16_t m2;           // usually an index to a town/industry/station
    uint8_t  m1, m3, m4, m5;  // general purpose bits
};
struct TileExtended {      // 4 more bytes
    uint8_t  m6, m7;
    uint16_t m8;
};

Those deliberately meaningless names — m1 through m8 — are raw storage. What any given bit means depends entirely on the tile's type. On a railway tile, some bits in m5 describe which track pieces are present; on a house tile the same bits mean something completely different.

The reason is arithmetic. The largest map is 4,096 × 4,096 tiles — nearly 16.8 million tiles. At 12 bytes each that is about 192 MB of map, and it must be walked constantly and saved to disk. A conventional object per tile, with a virtual function table and a pointer or two, would cost several times that and destroy cache locality in the tightest loops in the program.

The rule this creates Never read or write those bytes directly. Every tile type provides accessor functions in its *_map.h file — IsTileType(tile, MP_RAILWAY), GetTrackBits(tile), SetTileOwner(tile, owner). They encapsulate the bit layout, which is documented in docs/landscape.html. Poking at m5 by hand is how you corrupt a map silently.

5Pools: everything that moves

Tiles cover static terrain. Things with identity and a lifetime — vehicles, stations, towns, industries, orders, companies — live in pools.

A pool is a sparse array with stable index-based IDs. Create a vehicle and it takes the lowest free slot; delete it and the slot is freed for reuse. The ID is a plain number, which is precisely the point: it can be written into a saved game, sent over the network, and stored in a map tile's m2 field, and it will still mean the same thing when read back. A memory pointer could do none of that.

struct Vehicle : VehiclePool::PoolItem<&_vehicle_pool>, BaseVehicle, BaseConsist { ... };

That first line says "Vehicle is an item in the vehicle pool" — C++ inheritance used to bolt on the pool machinery. The practical consequences for anyone reading the code:

  • IDs are typed (VehicleID, StationID, TownID), not bare integers, so you cannot accidentally pass a station where a town belongs.
  • Each has an explicit ::Invalid() value rather than using zero or −1.
  • Pools are holey. Slot 5 existing does not mean slot 4 does. Always iterate with the pool's own iterator, never a counting loop.

6Commands

Here is the rule that shapes the whole program: nothing changes the game world except through a command. Not the interface, not the AI, not the network layer. Building a single piece of track is a command. So is renaming a station, buying a vehicle, or paying a loan.

Every command is written to run in two passes:

  1. Test pass. Work out whether this is legal and what it would cost — but change nothing.
  2. Execute pass. Do it for real.

The same function handles both, distinguished by a flag:

CommandCost CmdBuildSingleRail(DoCommandFlags flags, TileIndex tile, ...)
{
    if (!IsTileFlat(tile)) return CommandCost(STR_ERROR_FLAT_LAND_REQUIRED);

    // only actually modify the world on the execute pass
    if (flags.Test(DoCommandFlag::Execute)) {
        MakeRailNormal(tile, ...);
        MarkTileDirtyByTile(tile);
    }
    return CommandCost(EXPENSES_CONSTRUCTION, cost);
}

This buys two things at once. It gives the player a cost estimate and a red error message before committing — the test pass is what runs as you drag a tool across the map. And it gives the network layer a way to validate an incoming action before broadcasting it.

The classic bug Both passes must reach exactly the same verdict and the same price. If the test says "yes, £480" and the execute then fails or charges £500, some machines apply the change and others do not — and the multiplayer game breaks apart. Any condition checked in one pass must be checked in both.

7Determinism rules everything

Multiplayer works by sending a saved game to each joining client, then broadcasting only commands — each stamped with the exact tick it must execute on. Between commands, every machine simulates independently and must arrive at the same state. When they do not, it is called a desync, and it is the most feared class of bug in the project.

This produces a distinction that runs through the entire codebase: some state is part of the simulation, and some belongs only to the person sitting at this particular computer.

VariableKindSafe to read in command code?
_settings_gameSimulation — saved, identical everywhereyes
_current_companySimulation — who this command acts foryes
_settings_clientLocal — this person's preferencesnever
_local_companyLocal — who this person plays asnever

Anything unpredictable is likewise banned from the simulation: real time, uninitialised memory, pointer addresses, floating-point maths, the iteration order of a hash table. Money is stored as a 64-bit integer with overflow protection, never a floating-point number — partly for the usual rounding reasons, but also because floating-point results can differ between processors.

The two opposite reasons to ban rand()

OpenTTD forbids the standard random number generator, and the reason is the opposite of the usual one. Most codebases ban it because it is too predictable for security. OpenTTD bans it because it is not predictable enough.

The simulation uses a seeded generator whose state is saved in the game file, so every machine draws the identical sequence of "random" numbers. Meanwhile the network authentication code genuinely does need unpredictability, and uses a real cryptographic generator. Two rules, two code paths — and applying either one on the other's territory is a bug.

8How the AI works

The computer opponents are the most surprising part of the codebase, because they are not written in C++ and are not part of the program.

8.1  AIs are downloadable scripts

An AI is a third-party program written in Squirrel, a small scripting language similar in feel to JavaScript or Lua. Players download AIs from an in-game content service, and several can compete in the same game. The interpreter is embedded in OpenTTD; the AIs themselves are just files.

An AI cannot touch the world directly. It sees the game only through an API of roughly 150 classes — AIStation, AIRail, AIVehicle, AICargo and so on — and when it wants to do something, that call becomes a command, exactly the same command a human clicking a button would produce. This is why AI opponents obey the same rules, pay the same prices and are subject to the same failures as you are: there is no separate code path for them.

8.2  The opcode budget

Here is the problem the design has to solve. A downloaded script of unknown quality runs inside the game loop. If it enters an infinite loop, or spends four seconds pathfinding, the entire game freezes — and in multiplayer, every player freezes with it.

The solution is to never let a script run to completion. Instead, the AI is given a fixed budget of virtual-machine instructions, and when the budget runs out the interpreter suspends the script mid-execution — halfway through a function, inside a loop, wherever it happens to be. The game continues. On a later tick the script is resumed exactly where it stopped.

SettingValue
Default budget per slice10,000 opcodes
Minimum / maximum500 / 250,000
Garbage collectionOne AI every 255 ticks — roughly every two in-game months each

The script author never sees this happening. From inside the AI, the code appears to run continuously; in reality it is being frozen and thawed hundreds of times per in-game day. Overrunning the budget is tracked and charged against the next slice, so a script cannot cheat by writing one enormous instruction.

8.3  Deliberate slowness

A computer could issue thousands of build commands per second. That would be both unbeatable and unwatchable, so the AI is throttled twice over.

First, every command suspends the script. Not for a budget reason — deliberately. When an AI builds a piece of track, its execution stops for at least one tick before the next instruction runs. The source comment is candid about why: it simulates multiplayer latency, and it "gives time for the GUI and human player to interact with the game."

Second, the game's difficulty setting gates how often AIs get a slice at all:

AI::frame_counter++;
// competitor_speed 4 = every tick, 3 = every 2nd, 2 = every 4th ...
if ((AI::frame_counter & ((1 << (4 - competitor_speed)) - 1)) != 0) return;

At the slowest setting an AI thinks once every sixteen ticks. Difficulty here is not a cheat or a handicap applied to prices — it is literally how much thinking time the opponent is granted.

8.4  Two kinds of script, and a safety net

The same machinery runs a second kind of script, the GameScript, which is not a competitor but a scenario director — it sets goals, awards subsidies, displays messages and shapes the rules of a particular scenario.

The critical difference is authority. An AI is a company: it has money, owns vehicles, and its commands are charged to its account. A GameScript is a "deity": it has no company and acts on the world itself. Calling a company-scoped operation without a company is a crash.

Enforced automatically Because that mistake is easy to make and catastrophic, it is checked by a script in the project's continuous integration. Any API function that issues a command or asks which company it belongs to must declare which mode it requires — EnforceDeityMode, EnforceCompanyModeValid, or the variant accepting both. A function that forgets fails the build.

8.5  Keeping decade-old AIs alive

Published AIs are not maintained in step with the game, so the API is versioned — every release from 0.7 through 16 is still supported, and each script declares which version it was written against.

The trick that makes this affordable is a set of compatibility scripts: small Squirrel files, one per old version, loaded before the AI starts. Each one patches the current API back into the shape that version expected — restoring renamed functions, re-adding removed ones, adjusting changed return values. The file for version 15 describes itself plainly: "code to downgrade the API from 16 to 15." Rename an API function today, and you add a line to those files so that a decade of published AIs keep working.

8.6  Following one action all the way through

Putting the whole chain together — here is what happens when an AI decides to build a bus station:

  1. The AI's Squirrel code calls AIRoad.BuildRoadStation(tile, ...).
  2. The API layer checks it is in company mode, and validates the arguments.
  3. It builds the same command a human would generate and hands it to the command system.
  4. The command runs its test pass. If the tile is unsuitable or the company cannot afford it, an error comes straight back.
  5. In multiplayer the command is broadcast to be executed on an agreed future tick; in single-player it executes now.
  6. The script is suspended — execution stops mid-function.
  7. Ticks pass. Other AIs think, vehicles move, the world advances.
  8. The script resumes on the line after the call, and reads the result.

Steps 3 and 4 are the reason AI code needs no special handling anywhere in the simulation. By the time the world is touched, there is nothing left to distinguish an AI's action from a human's.

9Pathfinding

Every train, road vehicle and ship must repeatedly answer "which way now?". That work is done by YAPF — "Yet Another Path Finder", named in the tradition of having replaced two earlier attempts.

It is an A* search, but the interesting parts are the domain details. Rail pathfinding cannot treat the map as a grid of squares: it has to reason about which track direction a train occupies, because a train entering a tile heading north-east has different options than one heading south. It must account for signals, reserved sections held by other trains, station platform lengths, and whether the locomotive can even use that kind of track. Results are cached aggressively, since the same junction is evaluated constantly.

Ships get an extra layer. Open water has no track to constrain the search, so the map is first divided into large "water regions" and a coarse route between regions is found, before detailed pathfinding runs inside them — a two-level search that keeps ocean crossings affordable.

10Cargo and the economy

Cargo is not a number in a counter. It is tracked in packets, each recording where it came from, when, and what has been paid so far:

FieldPurpose
countHow many units in this packet
periods_in_transitHow long it has been travelling — older cargo pays less
source, source_xyOrigin industry or town, and its location, for distance-based payment
feeder_shareMoney already owed to earlier legs of a multi-vehicle journey
next_hopWhich station this cargo wants to travel to next

This granularity is what allows payment to depend on distance travelled and time taken, and lets a chain of vehicles each get a fair share of one delivery. It is also why a busy station holds thousands of small records rather than one integer per cargo type.

Deciding where cargo wants to go is a separate and much harder problem, handled by the link graph. Your stations and routes form a network, and distributing cargo across it optimally is a multi-commodity flow problem — formally NP-hard. The game runs it on a background thread, gives it a configurable number of in-game days to finish, and uses the previous answer until it does.

11Drawing the world

The visual style is 2D sprites in an isometric projection, and the rendering path reflects the game's age in a way that turns out to be a strength.

A blitter is the component that actually writes pixels. OpenTTD ships several and picks one at startup: an 8-bit paletted blitter matching the original 1995 graphics, 32-bit blitters for high-colour replacement art, and hand-written variants using SSE2, SSSE3 and SSE4 processor instructions where available. All implement the same interface, so the rest of the drawing code neither knows nor cares which is in use.

The same pattern — one interface, several implementations, chosen at runtime — is used for video output (SDL, Win32, Cocoa, OpenGL, or a null driver for headless servers), sound and music. It is what allows one codebase to run on Windows, macOS, Linux and in a web browser, and lets a dedicated server build simply select the null drivers and skip the graphics libraries entirely.

Sprites are loaded on demand into a cache with a least-recently-used eviction policy, because the full set of graphics with mods installed does not comfortably fit in memory. The viewport then turns world coordinates into screen coordinates and works out the draw order — genuinely fiddly in an isometric view, where a tall building on a low tile can obscure a train behind it.

12Text, settings, generated code

Three parts of the codebase do not exist until you build it. They are produced by small programs that run during compilation and write C++ source into the build directory.

Text is worth a closer look because of the scale. The game displays no literal strings — every message is an identifier like STR_ERROR_FLAT_LAND_REQUIRED, resolved at runtime against the player's chosen language. english.txt is the master list and the only one edited by hand; the other 65 languages are maintained by volunteer translators through a web service that syncs into the repository nightly.

If a symbol will not resolve When STR_SOMETHING or a setting name cannot be found, the fix is almost always in the source .txt or .ini file, not in the generated header — which is overwritten on every build.

13NewGRF: rewriting the game

NewGRF is OpenTTD's mod system, and it is unusually deep. A NewGRF file can replace graphics, but it can also add entirely new vehicles, industries, houses, station designs and cargo types, and attach behaviour to them — production rules, availability dates, appearance varying by climate, date or surroundings.

The format is inherited from the original game's modding scene and is essentially a small bytecode. Files are sequences of numbered "actions": action 0 sets properties on game objects, action 1 defines sprite sets, action 2 builds decision trees over them, action 3 binds those to a feature, and so on. The loader mirrors this exactly — newgrf_act0.cpp, newgrf_act1.cpp, up through newgrf_act14.cpp, with action 0 further split per feature because it carries the bulk of the work.

Two consequences worth knowing. Because mods change what exists in the world, the set of loaded NewGRFs is recorded in the saved game, and loading a save without them produces the warnings players are familiar with. And because the format is a contract with content authors going back twenty years, changes to it are made about as carefully as changes to the savegame format.

14Saving and loading

OpenTTD can still load games saved by versions from the early 2000s. Supporting that for two decades requires a strict discipline.

The savegame version is an enumeration whose position in the list is the version number written into the file. The current value is 366. The rules follow directly:

  • New entries are appended at the end, immediately before the terminator.
  • Nothing is ever reordered or deleted — doing so silently renumbers every later version and misreads every existing file.
  • Code that must behave differently for older files asks IsSavegameVersionBefore(...).

A saved game is a series of tagged chunks, each owned by the subsystem that understands it. Loading happens in two phases: chunks are read in, then a fix-up pass resolves stored numeric IDs back into usable references — necessary because a vehicle may refer to a station whose chunk had not yet been read. Finally afterload.cpp runs a long ordered chain of migrations, each guarded by a version check, upgrading the loaded state one version at a time until it matches what the current code expects.

Testing this properly Round-tripping a game you just saved proves only that the writer agrees with the reader. The real test is loading an old file. A save that loads but produces subtly different state is a desync waiting to happen in multiplayer.

15Where to start reading

Building it, on Windows with Visual Studio and the vcpkg package manager:

cmake -B build -G "Visual Studio 17 2022" ^
      -DCMAKE_TOOLCHAIN_FILE="...\vcpkg\scripts\buildsystems\vcpkg.cmake" ^
      -DVCPKG_TARGET_TRIPLET="x64-windows-static"
cmake --build build --config RelWithDebInfo

There are two test suites: a small set of unit tests covering the self-contained pieces (bit maths, string handling, the network handshake), and a much more important set of regression tests that run the game headless, drive the scripting API against a fixed saved game, and compare the output line by line against a recorded transcript. That second suite is the real safety net, and it works precisely because the simulation is deterministic — the same map must always produce the same result.
